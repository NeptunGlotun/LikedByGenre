## 1. Загальні положення та архітектурні принципи

Цей документ визначає стандарти проектування, написання коду, конвенції іменування (Naming Policy), а також перелік неприпустимих антипатернів (Anti-patterns) для проєкту **LikedByGenre (SSS)**.

**Технологічний стек:**
- **Платформа:** .NET 8 (C# 12)
- **Фреймворк:** ASP.NET Core MVC (контролери, Razor Views)
- **Доступ до даних:** Entity Framework Core 8 (`Microsoft.EntityFrameworkCore.SqlServer`)
- **База даних:** Microsoft SQL Server (локальний екземпляр, адміністрування через SSMS)
- **Зовнішня інтеграція:** Spotify Web API (OAuth 2.0 PKCE, REST API via `HttpClient`)
- **Середовище розробки:** Visual Studio 2022

**Архітектурний підхід:**
- Монолітний веб-додаток із модульною організацією за Bounded Contexts у єдиному проєкті (`Identity`, `Library`, `Classification`, `Playlists`, `Infrastructure`).
- Заборонено впроваджувати штучні шари абстракцій (зайві інтерфейси для сервісів без альтернативних реалізацій, патерн Repository поверх `DbSet`, що дублює EF Core).
- Простота, відсутність невикористовуваних технологій (жодного Docker, Kubernetes, microservices, Kafka, Redis тощо).

## 3. Anti-patterns (Антипатерни розробки)

Нижче наведено перелік критичних антипатернів, які суворо заборонено використовувати в кодовій базі проєкту.

### 3.1. C# та асинхронне програмування

1. **Async Void:**
   - *Суть помилки:* огошення методу як `public async void DoWork()`.
   - *Чому заборонено:* винятки, згенеровані всередині `async void`, неможливо перехопити через `try-catch`, що призводить до негайного падіння процесу веб-додатка.
   - *Правильне рішення:* завжди повертати `Task` або `Task<T>`. `async void` дозволений виключно для event handlers у десктоп/UI коді, який тут не використовується.
2. **Sync-over-Async (Блокування асинхронного коду):**
   - *Суть помилки:* виклики `.Result`, `.Wait()` або `.GetAwaiter().GetResult()` на завданнях `Task`.
   - *Чому заборонено:* призводить до блокування потоків пулу потоків (.NET Thread Pool Starvation) і виникнення взаємних блокувань (Deadlocks).
   - *Правильне рішення:* наскрізне використання `await` по всьому ланцюжку викликів аж до дій контролерів.
3. **Fire-and-Forget без обробки помилок:**
   - *Суть помилки:* виклик `_ = SomeAsyncTask()` без очікування та відстеження результату.
   - *Чому заборонено:* будь-яка помилка під час виконання завдання залишиться непоміченою, а стан даних у БД може стати неузгодженим.
   - *Правильне рішення:* очікувати виконання операцій через `await` із передачею `CancellationToken`.

### 3.2. Архітектура та ASP.NET Core

4. **Fat Controllers (Товсті контролери):**
   - *Суть помилки:* розміщення бізнес-логіки обробки треків, розбиття на сторінки, викликів Spotify HTTP API безпосередньо у методах контролерів.
   - *Чому заборонено:* контролер стає громіздким, важким для тестування і супроводу.
   - *Правильне рішення:* контролер відповідає лише за прийом HTTP-запиту, виклик сервісу (`LibraryImportService`, `PlaylistExportService`, `GenreClassificationService`) та повернення View/Redirect.
5. **Repository over EF Core (Штучний патерн репозиторію):**
   - *Суть помилки:* створення класів на зразок `TrackRepository : ITrackRepository`, які просто викликають `_context.Tracks.Add()` або `_context.Tracks.ToList()`.
   - *Чому заборонено:* `DbContext` уже є реалізацією Unit of Work, а `DbSet<T>` — репозиторієм. Створення додаткового шару приховує можливості LINQ, ускладнює оптимізацію запитів і створює зайвий код.
   - *Правильне рішення:* інжектувати `AppDbContext` безпосередньо у доменні сервіси.
6. **Service Locator:**
   - *Суть помилки:* передача `IServiceProvider` у класи та ручне викликання `serviceProvider.GetService<T>()`.
   - *Чому заборонено:* приховує залежності класу та ускладнює розуміння життєвого циклу об'єктів.
   - *Правильне рішення:* явне оголошення залежностей у конструкторі через Constructor Injection.

### 3.3. Робота з Entity Framework Core та базою даних

7. **N+1 Query Problem:**
   - *Суть помилки:* завантаження сутностей, а потім у циклі `foreach` виконання окремого SQL-запиту для кожної пов'язаної сутності (наприклад, для кожного треку окремо шукати артиста).
   - *Чому заборонено:* генерує сотні зайвих запитів до SQL Server і кардинально знижує продуктивність на вибірках у 2000+ треків.
   - *Правильне рішення:* використовувати жадібне завантаження (Eager Loading) через `.Include()` та `.ThenInclude()`, або проектувати дані через `.Select()`.
8. **Tracking Overhead на операціях лише для читання:**
   - *Суть помилки:* завантаження тисяч треків для відображення без виклику `.AsNoTracking()`.
   - *Чому заборонено:* EF Core відстежує стан кожної сутності в пам'яті (`ChangeTracker`), що споживає значні обсяги оперативної пам'яті та процесорного часу.
   - *Правильне рішення:* для запитів, що використовуються лише для показу або фільтрації, обов'язково застосовувати `.AsNoTracking()`.
9. **DbContext Concurrency / Multithreaded Access:**
   - *Суть помилки:* спроба паралельного використання одного екземпляра `AppDbContext` у кількох фонових потоках (`Task.WhenAll`).
   - *Чому заборонено:* екземпляри `DbContext` не є потокобезпечними (Thread-safe) і викидають `InvalidOperationException`.
   - *Правильне рішення:* послідовне виконання операцій у межах скоупу або створення окремого скоупу `IServiceScope` для кожної фонової операції.

### 3.4. Інтеграція з зовнішнім API (Spotify API)

10. **Hardcoded Secrets (Захардкоджені секрети):**
    - *Суть помилки:* розміщення `client_secret`, API токенів або паролів безпосередньо в коді чи у файлі `appsettings.json`.
    - *Чому заборонено:* призводить до компрометації облікових записів розробника при публікації репозиторію.
    - *Правильне рішення:* локальне використання .NET User Secrets (`dotnet user-secrets`).
11. **Brute-Force API Calling / Ignoring Rate Limits (Ігнорування лімітів 429):**
    - *Суть помилки:* надсилання сотень запитів без пауз і без перевірки заголовка `Retry-After`.
    - *Чому заборонено:* призводить до тимчасового блокування Spotify Client ID за перевищення лімітів (HTTP 429 Too Many Requests).
    - *Правильне рішення:* реалізація експоненційного очікування з урахуванням `Retry-After` (реалізовано в `SendWithRetryAsync`) та розбиття запитів артистів на невеликі пакети (по 40 артистів із паузою 80 мс).
12. **Unbounded Import (Непагіноване завантаження великих обсягів):**
    - *Суть помилки:* спроба завантажити всі 2000+ треків одним нерозривним HTTP-запитом без пагінації.
    - *Чому заборонено:* Spotify API повертає максимум 50 треків за один запит.
    - *Правильне рішення:* ітеративне завантаження сторінками з використанням параметрів `limit=50&offset={offset}` до моменту, поки `offset >= total`.

### 3.5. Обробка помилок та журналювання

13. **Swallowing Exceptions (Ковтання винятків):**
    - *Суть помилки:* порожні блоки `catch (Exception) { /* нічого */ }`.
    - *Чому заборонено:* помилка залишається непомітною, застосунок продовжує роботу в некоректному стані, відсутня можливість знайти причину збою.
    - *Правильне рішення:* логувати виняток або передавати зрозуміле повідомлення про помилку користувачеві через `TempData["Error"]`.
14. **Leaking Sensitive Data in Error Messages & Logs:**
    - *Суть помилки:* запис повних Bearer-токенів або чутливих заголовків у текстові логи чи виведення повного стек-трейсу користувачеві в UI.
    - *Чому заборонено:* загрожує витоком сесійних токенів.
    - *Правильне рішення:* обрізка помилок (`TrimError`), очищення заголовків авторизації та показ дружніх повідомлень про помилки у продакшен-режимі.
