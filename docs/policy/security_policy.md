## 1. Purpose

Метою цієї політики безпеки є встановлення чітких, обов'язкових і перевірюваних вимог безпеки для застосунку **LikedByGenre (SSS)** на етапах проектування, написання коду, тестування та локальної експлуатації.

**Основні цілі безпеки:**
- **Захист облікових даних та секретів:** недопущення витоку `Spotify:ClientSecret`, персональних Bearer-токенів (`access_token`, `refresh_token`) та рядків підключення до SQL Server у вихідний код, відкриті репозиторії Git, логи або HTTP-відповіді клієнту.
- **Безпечна автентифікація та сесії:** забезпечення надійної взаємодії зі Spotify Accounts Service за стандартом OAuth 2.0 з використанням Proof Key for Code Exchange (PKCE) та захищених cookie-сесій ASP.NET Core.
- **Цілісність та ізоляція локальних даних:** гарантування розмежування даних користувачів у базі даних SQL Server за `OwnerSpotifyId` та захист бази від несанкціонованого доступу та ін'єкцій.
- **Стійкість до збоїв зовнішніх сервісів:** безпечна обробка помилок Spotify Web API, включаючи ліміти частоти запитів (HTTP 429 Rate Limiting), без розкриття чутливої інформації в інтерфейсі користувача.

Політика є обов'язковою для дотримання автором лабораторної роботи, рев'юерами коду та ШІ-асистентами, задіяними у розробці.

## 2. Scope

Політика поширюється на всі складові частини програмного рішення `LikedByGenre`:

- **Вихідний код:** увесь C#-код у каталозі `src/LikedByGenre/` (контролери, сервіси, моделі даних, конфігурація `Program.cs`, Razor-шаблони `Views/`).
- **Сховища конфігурації:** файли `appsettings.json`, `appsettings.Development.json`, профіль запуску `launchSettings.json` та сховище .NET User Secrets (`secrets.json`).
- **База даних:** локальний екземпляр Microsoft SQL Server (доступний через SSMS / LocalDB / SQLEXPRESS) та схема даних, керована Entity Framework Core (`AppDbContext`).
- **Зовнішні комунікації:** взаємодія через HTTPS з Spotify Accounts Service (`https://accounts.spotify.com/`) та Spotify Web API (`https://api.spotify.com/v1/`).
- **Середовище запуску:** локальна машина розробника (Visual Studio 2022 / .NET 8 SDK / Windows).
- **Документація:** уся супровідна інженерна документація в каталозі `docs/`.

**Явні виключення зі скоупу:**
- Проєкт не містить хмарного хостингу (AWS, Azure, GCP), Docker-контейнеризації, Kubernetes, брокерів черг повідомлень (RabbitMQ, Kafka), distributed-кешу (Redis) або білінгових систем. Захист таких компонентів явно не розглядається.

## 4. Security Principles

Розробка та конфігурація проєкту базуються на таких фундаментальних принципах:

1. **No Secrets in Source Code (Нуль секретів у коді):** жоден приватний ключ, клієнтський секрет (`ClientSecret`), токен доступу чи пароль до бази даних не фіксується у файлах коду або системі контролю версій Git.
2. **Least Privilege (Мінімальні привілеї):** застосунок запитує у Spotify виключно ті OAuth-скоупи, які мінімально необхідні для виконання бізнес-завдань:
   - `user-library-read` — для читання списку вподобаних треків;
   - `playlist-modify-private` та `playlist-modify-public` — для створення нових плейлистів за жанрами;
   - `user-read-private` — для отримання ідентифікатора та імені користувача.
3. **Secure by Default & Deny by Default:**
   - Усі сторінки та контролери окрім `Home/Index`, `Home/Error` та `Account/Login` вимагають обов'язкової автентифікації. Неавтентифіковані запити автоматично перенаправляються на сторінку входу.
   - Запити на зміну стану (імпорт треків, підтягування жанрів, експорт плейлистів) приймаються виключно через HTTP POST із валідацією Anti-Forgery Token (CSRF-захист).
4. **Fail Securely (Безпечна відмова):**
   - У разі вичерпання лімітів Spotify API (HTTP 429) або мережевого збою клієнту повертається безпечне інформативне повідомлення без деталізації чутливих технічних заголовків та стек-трейсів.
   - За відсутності валідної сесії чи простроченому токені користувач безпечно спрямовується на повторний вхід.
5. **Data Isolation (Ізоляція даних):**
   - Усі запити до бази даних SQL Server для вибірки або модифікації треків та експортів обов'язково фільтруються за `OwnerSpotifyId`, що унеможливлює витік даних між різними сесіями.

## 5. Secure Development Environment

Вимоги до локального робочого місця та середовища розробки:

- **Контроль вихідного коду (Git):**
  - Файл `.gitignore` проєкту повинен обов'язково блокувати потрапляння у репозиторій артефактів збірки (`bin/`, `obj/`), тимчасових файлів Visual Studio (`.vs/`), локальних параметрів запуску та секретів користувача.
- **Управління секретами розробника:**
  - Значення `Spotify:ClientId` та `Spotify:ClientSecret` зберігаються у локальному файлі User Secrets операційної системи (поза деревом репозиторію) через команду:
    ```bash
    dotnet user-secrets set "Spotify:ClientId" "<your_id>"
    dotnet user-secrets set "Spotify:ClientSecret" "<your_secret>"
    ```
  - У файлі `appsettings.json` значення секретів залишаються порожніми рядками (`""`).
- **Безпека підключення до бази даних:**
  - Використовується Windows Authentication (`Trusted_Connection=True;TrustServerCertificate=True`), що усуває потребу у зберіганні логінів та паролів до SQL Server у рядку підключення.
- **Безпека транспорту:**
  - Локальний запуск здійснюється через HTTPS (сертифікат `dotnet dev-certs https`).

  - Метод `TrimError` у `SpotifyApiClient` обрізає тексти помилок зовнішнього API до 300 символів та не включає чутливі параметри запиту.

## 7. Secure Implementation

Вимоги до безпечної програмної реалізації на рівні C# та ASP.NET Core:

1. **Автентифікація, паролі та сесії:**
   - **Локальне безпечне збереження паролів:** паролі локальних користувачів ніколи не зберігаються у відкритому вигляді; використовується алгоритм **BCrypt** з автоматичним формуванням криптографічної солі та параметром вартості (workFactor = 12). Для перевірки входу використовується `BCrypt.Net.BCrypt.Verify()`. При помилці автентифікації повертається узагальнене повідомлення для запобігання перебору імен.
   - **Федеративний вхід:** інтеграція зі Spotify Accounts Service за стандартом OAuth 2.0 з використанням PKCE (`options.UsePkce = true`).
   - Cookie сесії `LikedByGenre.Auth` налаштована із прапорцями безпеки:
     - `HttpOnly = true` — захист від крадіжки токенів сесії через XSS у браузері;
     - `SameSite = SameSiteMode.Lax` — захист від CSRF під час навігації;
     - `SecurePolicy = CookieSecurePolicy.SameAsRequest` — передача захищеним каналом;
     - `ExpireTimeSpan = TimeSpan.FromHours(8)` з увімкненим ковзним терміном дії (`SlidingExpiration = true`).
2. **Захист від ін'єкцій (SQL Injection):**
   - Усі звернення до SQL Server реалізуються виключно через Entity Framework Core (LINQ-запити із автоматичною параметризацією). Сирий SQL (`FromSqlRaw`, `ExecuteSqlRaw`) без параметризації суворо заборонений.
3. **Захист від міжсайтової підробки запитів (CSRF):**
   - Усі форми, що змінюють стан (виклик `/Account/Logout`, `/Library/ImportTracks`, `/Library/FetchGenres`, `/Playlists/Export`), захищені валідацією Anti-Forgery Token ASP.NET Core (`[ValidateAntiForgeryToken]`).
4. **Валідація та санітизація вхідних даних:**
   - Зовнішні ідентифікатори треків, артистів та плейлистів перевіряються на довжину та допустимі символи відповідно до обмежень моделі (`HasMaxLength` у `AppDbContext`).
   - Дані, отримані від Spotify API, десеріалізуються через типізовані DTO з перевіркою на `null`.
5. **Безпечна робота з зовнішнім API (Resilience):**
   - Реалізовано обробку статусу HTTP 429 з підтримкою заголовка `Retry-After` (експоненційне очікування замість перевантаження зовнішнього сервісу).
   - Між послідовними запитами до `/v1/artists/{id}` впроваджено паузу (80 мс), що запобігає блокуванню акаунта розробника.

## 8. Security Verification

Перевірка безпекових вимог здійснюється такими засобами:

- **Статичний аналіз коду:**
  - Регулярна перевірка коду вбудованими аналізаторами Visual Studio та Roslyn Analyzers при компіляції (`dotnet build`). Нульова толерантність до попереджень компілятора щодо безпеки та `null-safety` (`<Nullable>enable</Nullable>`).
- **Перевірка відсутності секретів (Secret Scanning):**
  - Обов'язкова перевірка `git status` та `git diff` перед створенням коміту для гарантування відсутності файлів `secrets.json`, заповнених `appsettings.json` або тимчасових ключів.
- **Тестування автентифікації та меж авторизації:**
  - Ручне тестування спроби відкриття `/Library`, `/Genres`, `/Playlists` анонімним користувачем (перевірка перенаправлення на `/Account/Login`).
  - Перевірка коректності фільтрації даних за `OwnerSpotifyId` у SQL Server через SSMS.

## 9. Vulnerability Management

Процедура реагування на виявлені потенційні дефекти безпеки:

1. **Реєстрація:** при виявленні вразливості (наприклад, застаріла залежність NuGet із відомим CVE, витік токена або помилка валідації вводу) проблема фіксується розробником із зазначенням ураженого компонента.
2. **Пріоритизація та усунення:**
   - Критичні проблеми (компрометація секрету) усуваються негайно: відкликання Client Secret у Spotify Dashboard, перевипуск нового секрету, оновлення User Secrets.
   - Оновлення пакетів NuGet проводиться через NuGet Package Manager у Visual Studio до стабільних версій без вразливостей.
3. **Верифікація:** повторна перевірка працездатності автентифікації та імпорту після виправлення.

## 10. Privacy Policy

Політика конфіденційності та обробки даних користувача:

- **Категорії даних:** застосунок опрацьовує:
  - Spotify User ID та Display Name (виключно для ідентифікації сесії та зв'язку треків із власником);
  - Метадані лайкнутих треків: назва треку, ім'я артиста, назва альбому, тривалість, дата додавання, жанрові теги артиста, Spotify URI;
  - Створені плейлисти (ідентифікатор плейлиста в Spotify та час створення).
- **Обмеження обробки:**
  - Застосунок НЕ збирає і не зберігає: паролі від Spotify, електронні пошти, платіжну інформацію, історію прослуховувань чи приватні повідомлення.
- **Місце зберігання:**
  - Усі дані зберігаються виключно локально у власній базі даних SQL Server на комп'ютері користувача.
  - Жодні дані не передаються на сторонні сервери чи аналітичні платформи (окрім прямих викликів офіційного Spotify API).
- **Видалення даних:**
  - За потреби всі збережені треки користувача та історія експорту можуть бути очищені шляхом видалення записів з таблиць у SSMS або перезапуску `EnsureCreated()`.
