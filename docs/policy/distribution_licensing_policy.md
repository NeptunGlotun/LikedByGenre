# Політика розповсюдження та ліцензування програмного забезпечення LikedByGenre (SSS)

## 1. Загальні положення та мета політики

Дана політика регламентує модель розповсюдження, правила надання доступу, механізми контролю дотримання ліцензійних умов та криптографічний захист програмного забезпечення **LikedByGenre (SSS — Simple Songs Sorting)** від несанкціонованого копіювання, модифікації параметрів ліцензій (tampering) та нелегітимного використання.

Документ встановлює вимоги до:
1. Вибору та обґрунтування моделі комерціалізації та дистрибуції.
2. Криптографічного формату ліцензійного файлу.
3. Генерації, збереження та управління життєвим циклом ключів ліцензування.
4. Верифікації автентичності та цілісності ліцензії в клієнтському та серверному середовищах.

## 2. Аналіз моделей розповсюдження програмного забезпечення

У сучасній інженерії програмного забезпечення застосовуються різні моделі надання прав на використання ПЗ:

| Модель | Характеристика | Переваги | Обмеження / Ризики |
| :--- | :--- | :--- | :--- |
| **Freeware** | Повністю безкоштовне використання без обмежень у часі чи функціоналі. | Швидке зростання користувацької бази, відсутність бар'єру входу. | Відсутність прямої монетизації, залежність від донатів чи реклами. |
| **Shareware** | Пробне безкоштовне використання з подальшою необхідністю придбання. | Можливість оцінити продукт перед купівлею. | Застарілий підхід; ризик зламу ліцензійного механізму. |
| **Trialware** | Повний функціонал, обмежений часовим проміжком (наприклад, 14 або 30 днів). | Повноцінна демонстрація можливостей продукту. | Відтік користувачів після закінчення терміну; потрібна верифікація часу. |
| **Demoware** | Безстрокове використання суворо обмеженої демонстраційної версії. | Захист ключового функціоналу від зламу (його фізично немає в збірці). | Користувач не може оцінити критичні функції в реальних сценаріях. |
| **Crippleware** | Продукт працює, але ключові функції (наприклад, збереження, експорт) заблоковані. | Стимулює негайний перехід на платну версію. | Негативний досвід користувача (UX friction). |
| **Freemium** | Базовий функціонал безкоштовний назавжди, розширені можливості (Pro/Enterprise) платні. | Висока віральність, лояльність, плавний перехід до оплати. | Необхідність чіткого балансу між безкоштовним і платним функціоналом. |
| **Subscription (Підписка)** | Регулярна періодична оплата (щомісячно/щороку) за право використання та оновлення. | Стабільний прогнозований дохід (ARR/MRR), постійна підтримка. | Потрібен постійний моніторинг активності підписки. |
| **Perpetual (Безстрокова)** | Одноразова покупка фіксованої версії безстроково. | Зрозумілість для консервативних корпоративних замовників. | Дохід лише один раз; висока вразливість до реверс-інжинірингу. |
| **SaaS (Software-as-a-Service)** | Доступ до ПЗ як до хмарної служби через веб-інтерфейс або API. | Централізоване оновлення, відсутність потреби у встановленні, захист вихідного коду. | Потрібна висока доступність серверної інфраструктури (SLA 99.9%). |

## 3. Обґрунтування вибору моделі для LikedByGenre (SSS)

Для системи **LikedByGenre (SSS)** обрано гібридну модель: **SaaS + Freemium + Subscription**.

### Обґрунтування вибору:
1. **Інтеграція з хмарними API (Spotify Web API):** Оскільки застосунок взаємодіє з потоковими даними музичного сервісу та виконує OAuth-авторизацію, хмарна модель (SaaS) забезпечує безпеку збереження клієнтських секретів (`client_secret`), захист токенів у серверних захищених сховищах та позбавляє користувача потреби налаштовувати локальне середовище.
2. **Freemium-план (Community Tier):** Дозволяє будь-якому користувачеві безкоштовно авторизуватися через Spotify, синхронізувати до 100 треків та створити до 3 жанрових плейлистів. Це забезпечує вірусне поширення та ознайомлення з алгоритмами класифікації.
3. **Pro-Subscription план (Комерційна підписка):** Надає доступ до пакетного експорту (`BatchProcessing`), розширеної аналітики жанрів (`AdvancedAnalytics`), обробки до 10 000 треків та необмеженої кількості експортів. Періодичність оплати покриває витрати на хмарну інфраструктуру, базу даних та трафік.

## 4. Криптографічний захист ліцензій: Порівняльний аналіз (MDC vs MAC vs ЕЦП)

Для забезпечення контролю ліцензійних обмежень та захисту від несанкціонованого копіювання було проаналізовано три криптографічні підходи:

```
[Порівняння криптографічних засобів захисту ліцензій]

1. Код виявлення модифікацій (MDC / Хеш-функція):
   [ Ліцензія JSON ] ---> SHA-256 ---> [ Hash ]
   Зловмисник змінює "max_tracks": 999999, обчислює новий SHA-256 і замінює хеш.
   ЗАХИСТ ВІДСУТНІЙ!

2. Код автентифікації повідомлень (MAC / HMAC-SHA256):
   [ Ліцензія JSON ] + [ Спільний секретний ключ K ] ---> HMAC ---> [ MAC ]
   Проблема: Клієнтська програма має перевірити MAC. Отже, ключ K повинен міститися
   у клієнті. Зловмисник декомпілює застосунок, витягує ключ K та генерує валідні MAC
   для будь-яких фальшивих ліцензій!

3. Асиметричний цифровий підпис (ЕЦП / RSA-PSS SHA-256):
   [ Ліцензія JSON ] + [ ПРИВАТНИЙ КЛЮЧ (Тільки на сервері вендора) ] ---> Sign ---> [ Signature ]
   Клієнт отримує ТІЛЬКИ ВІДКРИТИЙ КЛЮЧ:
   [ Ліцензія JSON ] + [ Signature ] + [ ВІДКРИТИЙ КЛЮЧ ] ---> Verify ---> OK / FAIL
   ВІДКРИТИЙ КЛЮЧ дозволяє лише перевіряти, але НЕ дозволяє створювати підписи!
   ПОВНА КРИПТОГРАФІЧНА СТІЙКІСТЬ!
```

### Висновок:
* **MDC (хеш)** не захищає від підробки, оскільки не містить секрету.
* **MAC (симетричний)** непридатний для розподіленого ПЗ, оскільки компрометація одного клієнтського екземпляра дає можливість генерувати ліцензії для всіх.
* **Електронний цифровий підпис (RSA-PSS / ECDSA)** є **єдино надійним** стандартом захисту розподілених ліцензійних файлів.

## 5. Специфікація реалізації RSA-PSS у LikedByGenre

### 5.1. Криптографічні параметри
* **Алгоритм:** RSA (Rivest-Shamir-Adleman) з імовірнісною схемою доповнення PSS (Probabilistic Signature Scheme, PKCS#1 v2.2 / RFC 8017).
* **Розмір ключа:** 3072 біти (забезпечує криптографічну стійкість понад 128 біт безпеки відповідно до рекомендацій NIST SP 800-57, актуально до 2030+ року).
* **Геш-алгоритм:** SHA-256 (Secure Hash Algorithm 256-bit).
* **Довжина солі (Salt Length):** Дорівнює розміру гешу (32 байти), що забезпечує максимальну стійкість проти атак відновлення повідомлення.

### 5.2. Формат файлу ліцензії (`license.json`)
```json
{
  "product_id": "LikedByGenre-SSS",
  "license_id": "LIC-2026-PZ41-0001-RYABCHUK",
  "licensee": "Рябчук Ігор (група ПЗ-41, варіант 1)",
  "tier": "Pro-Subscription",
  "issued_at": "2026-10-26T00:00:00Z",
  "valid_until": "2026-12-31T23:59:59Z",
  "max_tracks": 10000,
  "max_playlists": 100,
  "features": [
    "LibrarySync",
    "AutoClassification",
    "PlaylistExport",
    "AdvancedAnalytics",
    "BatchProcessing"
  ]
}
```

### 5.3. Файл підпису (`license.sig`)
Бінарний файл розміром 384 байти (3072 біти), що містить числовий блок підпису RSA-PSS.

## 6. Процедура управління ключами та верифікації

1. **Генерація пари ключів:** Проводиться вендором на ізольованому сервері ліцензування:
   ```bash
   openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out private.pem
   openssl rsa -pubout -in private.pem -out public.pem
   ```
2. **Зберігання закритого ключа (`private.pem`):** Зберігається у безпечному апаратному модулі безпеки (HSM) або захищеному сховищі секретів (Azure Key Vault / AWS KMS) з обмеженим доступом. Суворо заборонено поширювати разом із кодом програми.
3. **Розповсюдження відкритого ключа (`public.pem`):** Вбудовується безпосередньо у бінарні збірки ПЗ та постачається у каталозі `Licenses/public.pem`.
4. **Алгоритм валідації на боці системи:**
   * Зчитування `license.json` та `license.sig`.
   * Верифікація за допомогою `RSA.VerifyData(..., HashAlgorithmName.SHA256, RSASignaturePadding.Pss)`.
   * Якщо результат `false` — перехід в аварійний або демо-режим з попередженням про порушення цілісності.
   * Якщо `true` — перевірка полів `product_id`, `issued_at`, `valid_until` та застосування тарифних лімітів (`max_tracks`, `max_playlists`, `features`).
