### 2.2. Генерація пари асиметричних ключів RSA 3072 біти (Пункт 3)

За допомогою утиліти **OpenSSL 3.5.7** згенеровано криптографічно стійку пару ключів стандарту RSA довжиною 3072 біти (що забезпечує понад 128 бітів симетричної стійкості згідно з NIST SP 800-57):

```bash
# 1. Генерація закритого ключа (private key)
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out private.pem

# 2. Експорт відкритого ключа (public key) у форматі X.509 SubjectPublicKeyInfo
openssl pkey -in private.pem -pubout -out public.pem
```

### 2.3. Формування цифрового підпису RSA-PSS із SHA-256 (Пункт 4)

Згенеровано бінарний файл цифрового підпису `license.sig` за схемою **RSA-PSS** (Probabilistic Signature Scheme, PKCS#1 v2.2 / RFC 8017) з використанням хеш-функції **SHA-256** та довжини солі, рівної довжині хеш-дайджесту (32 байти):

```bash
openssl dgst -sha256 -sign private.pem -sigopt rsa_padding_mode:pss -sigopt rsa_pss_saltlen:digest -out license.sig license.json
```

Файл `license.sig` має розмір **384 байти** ($3072 \text{ біти} / 8$).

### 2.4. Верифікація автентичності еталонної ліцензії (Пункт 5)

Виконано перевірку сформованого підпису за допомогою відкритого ключа `public.pem`:

```bash
openssl dgst -sha256 -verify public.pem -signature license.sig -sigopt rsa_padding_mode:pss -sigopt rsa_pss_saltlen:auto license.json
```

**Результат виконання команди:**
```
Verified OK
```

Висновок: Цифровий підпис повністю валідний; дані ліцензії `license.json` є автентичними та підтвердженими правовласником закритого ключа.

### 2.6. Теоретичне обґрунтування: Чому ЕЦП перевершує MDC та MAC для контролю ліцензій

| Критерій | MDC (Код виявлення модифікацій / Хеш) | MAC (Код автентифікації / HMAC) | ЕЦП (Цифровий підпис / RSA-PSS) |
| :--- | :--- | :--- | :--- |
| **Криптографічна база** | Несиметрична геш-функція (SHA-256) без ключів. | Симетричний спільний секретний ключ ($K$). | Асиметрична пара ключів ($K_{priv}$ / $K_{pub}$). |
| **Місце збереження секрету** | Секрет відсутній. | Спільний ключ $K$ повинен зберігатися в клієнтській програмі для верифікації. | $K_{priv}$ зберігається **виключно у вендора**; у клієнт передається лише $K_{pub}$. |
| **Стійкість до модифікації ліцензії** | **Нульова**. Зловмисник змінює файл і сам обчислює новий SHA-256. | **Низька у відкритому середовищі**. Клієнтська програма декомпілюється, ключ $K$ вилучається з пам'яті, зловмисник підписує будь-які ліцензії. | **Абсолютна (математично доведена)**. Знаючи відкритий ключ $K_{pub}$, обчислити закритий ключ $K_{priv}$ за поліноміальний час неможливо ($2^{128}$ операцій). |
| **Придатність для масового розповсюдження** | Непридатний для контролю прав. | Непридатний (компрометація одного клієнта ламає всю систему). | **Ідеально придатний та загальноприйнятий індустріальний стандарт**. |

#### Графічна схема принципової відмінності:
```
+-----------------------------------------------------------------------------+
|                          ПРИНЦИП ЕЦП (RSA-PSS)                              |
+-----------------------------------------------------------------------------+
 СЕРВЕР ВЕНДОРА (Довірена зона):
 [ Ліцензія license.json ] + [ Закритий ключ private.pem ]
                 |
                 v (RSA-PSS SHA-256 Sign)
         [ Підпис license.sig ]
                 |
                 +-----------------------+
                                         | Постачання користувачу
                                         v
 КЛІЄНТСЬКИЙ ЗАСТОСУНОК (Недовірене середовище):
 [ license.json ] + [ license.sig ] + [ ВІДКРИТИЙ КЛЮЧ public.pem ]
                 |
                 v (RSA-PSS Verify)
       [ РЕЗУЛЬТАТ: ПІДТВЕРДЖЕНО (OK) / ПІДРОБКА (FAIL) ]

 Важливо: Користувач може аналізувати код та пам'ять застосунку, але наявність
 відкритого ключа public.pem НЕ ДОЗВОЛЯЄ згенерувати валідний license.sig!
+-----------------------------------------------------------------------------+
```

## 3. АНАЛІЗ ТА ОБҐРУНТУВАННЯ МОДЕЛІ РОЗПОВСЮДЖЕННЯ (ПУНКТИ 8–11)

### 3.1. Порівняльний аналіз моделей розповсюдження ПЗ

| Модель | Опис | Переваги | Ризики та недоліки |
| :--- | :--- | :--- | :--- |
| **Freeware** | Безоплатне поширення без обмежень часу. | Швидка популяризація продукту. | Відсутність прямої монетизації. |
| **Shareware** | Умовно-безкоштовне ПЗ (ознайомлення перед оплатою). | Зниження бар'єру покупки. | Схильність до патчингу та зламу перевірок. |
| **Trialware** | Повна версія з обмеженням за часом (наприклад, 14 днів). | Повна оцінка функціоналу користувачем. | Потребує захисту системного годинника від відкату. |
| **Demoware** | Демо-версія з вирізаними ключовими функціями. | Захист алгоритмів від зламу. | Гірший користувацький досвід. |
| **Crippleware** | Програма працює, але блокує фінальні дії (збереження). | Спонукає до миттєвої покупки. | Високе роздратування користувачів. |
| **Freemium** | Базовий функціонал безкоштовний завжди, преміум — за плату. | Масовість, висока конверсія. | Потребує суворого розмежування лімітів. |
| **Subscription** | Регулярна оплата за період використання. | Прогнозований постійний дохід (MRR). | Необхідність безперервної підтримки та оновлень. |
| **Perpetual** | Одноразова купівля безстрокової ліцензії на версію. | Зрозумілість для консервативних клієнтів. | Ризик піратства, відсутність доходу з підтримки. |
| **SaaS** | Програмне забезпечення як послуга в хмарі. | Захист вихідного коду, централізований контроль. | Витрати на серверну інфраструктуру, вимоги до SLA. |

---

### 3.2. Вибір та обґрунтування моделі для LikedByGenre (SSS)

Для системи **LikedByGenre (SSS)** обрано гібридну модель: **SaaS + Freemium + Pro-Subscription**.

1. **Архітектура SaaS:** Застосунок працює через веб-інтерфейс, підключаючись до Spotify API. Секрети додатку (`ClientSecret`) та конфіденційні сесійні токени ніколи не передаються в незахищений браузер, а зберігаються на захищеному сервері.
2. **Рівень Freemium (Community Tier):** Безкоштовний доступ для будь-якого користувача Spotify:
   - Синхронізація до 100 треків з медіатеки.
   - Створення до 3 жанрових плейлистів.
   - Базова класифікація за 4 основними жанрами (Rock, Pop, Electronic, Jazz).
3. **Рівень Pro-Subscription (Комерційна ліцензія):**
   - Розширена обробка до 10 000 треків.
   - Необмежений експорт плейлистів (до 100 одночасно).
   - Пакетна обробка (`BatchProcessing`) та розширена аналітика піджанрів (`AdvancedAnalytics`).
   - Підтвердження статусу через підписаний файл ліцензії `license.json` + `license.sig`.

## 4. ПРОГРАМНА РЕАЛІЗАЦІЯ ПІДСИСТЕМИ ЛІЦЕНЗУВАННЯ В ASP.NET CORE 8 (ПУНКТИ 12–13)

### 4.1. Архітектура компонентів

У проєкт `LikedByGenre` додано такі компоненти:
- `Models/LicenseInfo.cs` — модель ліцензійних параметрів (`ProductId`, `LicenseId`, `Licensee`, `Tier`, `IssuedAt`, `ValidUntil`, `MaxTracks`, `MaxPlaylists`, `Features`) та результат верифікації `LicenseValidationResult`.
- `Services/ILicenseValidationService.cs` — контракт служби верифікації.
- `Services/RsaPssLicenseValidationService.cs` — криптографічна служба перевірки цифрового підпису за допомогою вбудованого класу .NET `System.Security.Cryptography.RSA` з використанням `RSASignaturePadding.Pss` та `HashAlgorithmName.SHA256`.
- `Controllers/LicenseController.cs` — веб-контролер для відображення поточної ліцензії та інтерактивної верифікації завантажених файлів ліцензій.
- `Views/License/Index.cshtml` — інтерфейс користувача з бейджами статусу, таблицею параметрів, прогрес-барами та формою тестування підпису.

### 4.2. Фрагмент криптографічної перевірки підпису RSA-PSS у C#

```csharp
// 1. Криптографічна перевірка підпису RSA-PSS (SHA-256)
byte[] dataBytes = Encoding.UTF8.GetBytes(licenseJson);
bool isSignatureValid = _rsaPublic.VerifyData(
    dataBytes,
    signatureBytes,
    HashAlgorithmName.SHA256,
    RSASignaturePadding.Pss); // RFC 8017 / PKCS#1 v2.2

if (!isSignatureValid)
{
    return new LicenseValidationResult(
        false, 
        "InvalidSignature", 
        "Криптографічний підпис недійсний! Файл ліцензії було несанкціоновано модифіковано або підроблено.");
}

// 2. Десеріалізація та логічна перевірка параметрів
var license = JsonSerializer.Deserialize<LicenseInfo>(licenseJson);
if (!string.Equals(license.ProductId, ExpectedProductId, StringComparison.OrdinalIgnoreCase))
{
    return new LicenseValidationResult(false, "ProductMismatch", "Ліцензія належить іншому продукту.");
}

if (DateTime.UtcNow > license.ValidUntil)
{
    return new LicenseValidationResult(false, "Expired", "Термін дії ліцензії вичерпано.");
}

return new LicenseValidationResult(true, "Active", "Ліцензія дійсна. Автентичність підтверджено цифровим підписом RSA-PSS.", license);
```
