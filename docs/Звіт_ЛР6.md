## 2. ПРАКТИЧНЕ ДОСЛІДЖЕННЯ РЕЖИМУ AES-CTR ТА АТАКА ВІДОМОГО ВІДКРИТОГО ТЕКСТУ (ПУНКТИ 2–6)

### 2.1. Формування вхідних даних та шифрування AES-CTR (Пункти 2–4)

Згідно з регламентом лабораторної роботи сформовано текстовий рядок за шаблоном `«[поточний_рік]_[група]_[прізвище]_[ім’я]_варіант:[номер_варіанту]»`. Для варіанта 1 номер доповнено нулем попереду (`«01»`).

- **Початковий рядок ($P_1$):** `2026_ПЗ-41_Рябчук_Ігор_варіант:01`  
  Розмір у кодуванні UTF-8: **54 байти** (кириличні символи кодуються по 2 байти).  
  Шістнадцяткове представлення ($P_1$ у HEX):  
  `323032365F D09FD097 2D34315F D0A0D18F D0B1D187 D183D0BA 5FD086D0 B3D0BED1 805FD0B2 D0B0D180 D196D0B0 D0BDD182 3A3031`

Згенеровано випадковий 128-бітний симетричний ключ (**Ключ №1**) та початковий вектор лічильника (**Вектор №1 / IV**):

- **Шифротекст №1 ($C_1$, HEX):**

### 2.2. Реалізація атаки повторного використання лічильника (Known-Plaintext Attack, Пункт 5)

Режим CTR перетворює блоковий шифр на потоковий: блоковий шифр шифрує послідовність блоків лічильника $CTR, CTR+1, \dots$ за допомогою ключа $K$, формуючи псевдовипадкову ключову гаму $G = E_K(IV)$. Потім відкритий текст об'єднується з гамою за допомогою операції XOR:
$$C = P \oplus G$$

#### Крок 5.1–5.2: Відновлення гами без знання ключа
Оскільки зловмиснику відома пара $(P_1, C_1)$, завдяки властивості операції XOR ($A \oplus B \oplus B = A$), ключова гама відновлюється тривіально:
$$G_1 = C_1 \oplus P_1$$

- **Відновлена Гама №1 ($G_1$, HEX):**  
  `A7104E116505C070154AC1574AF0BA320433A50D08AB6AA6DA6C9253D6C27A2990E84C153D65597279674C3EAE220216A6A82854`

Порівняння відновленої гами $G_1$ з фактичною гамою, згенерованою шифром AES, показало **100% ідентичність** (`gammaMatch = True`).

#### Крок 5.3–5.4: Формування та підробка альтернативного повідомлення
Сформовано альтернативний відкритий текст із варіантом 99:
- **Альтернативний відкритий текст ($P_2$):** `2026_ПЗ-41_Рябчук_Ігор_варіант:99`

Маючи відновлену гаму $G_1$ та не знаючи ані байта секретного ключа $K$, зловмисник формує дійсний шифротекст для довільного повідомлення $P_2$:
$$C_2 = G_1 \oplus P_2$$

- **Підроблений Шифротекст №2 ($C_2$, HEX):**  
  `95207C273AD55FA08267F56615201AE38BE314DC8F7AE976603342D50671AA97416813C58FB5E9A3F9B6DAEE1EF2BFC72492116D`

Зверніть увагу: Шифротекст №1 та Шифротекст №2 відрізняються **лише в останніх двох байтах** (`1865` проти `116D`), що відповідає зміні символів `'01'` на `'99'`. Це наочно демонструє відсутність дифузії в режимі CTR.

### 2.3. Перевірка результатів атаки та розшифрування (Пункт 6)

Підроблений шифротекст $C_2$ передано на легітимну сторону, де його було розшифровано за допомогою оригінального **Ключа №1** та **Вектора №1**:
$$P'_{2} = C_2 \oplus E_{K_1}(IV_1) = (G_1 \oplus P_2) \oplus G_1 = P_2$$

- **Результат розшифрування $C_2$ легітимним ключем:**  
  `"2026_ПЗ-41_Рябчук_Ігор_варіант:99"`
- **Успішність атаки:** **`True` (100% успіх атаки)**

#### Висновки щодо режиму CTR та необхідності AEAD:
1. **Вразливість пластичності (Malleability):** Режим CTR забезпечує конфіденційність, але **категорично не забезпечує цілісності та автентичності**. Будь-яка зміна біта шифротексту призводить до передбачуваної зміни відповідного біта відкритого тексту після розшифрування.
2. **Фатальність повторного використання IV/Nonce:** Якщо той самий вектор ініціалізації $IV$ застосовується більше одного разу з одним ключем $K$, зловмисник здатний:
   - відновлювати відкритий текст без ключа ($C_A \oplus C_B = P_A \oplus P_B$);
   - підробляти зашифровані повідомлення, які успішно приймаються системою.
3. **Вимога безпеки:** У сучасному програмному забезпеченні звичайне шифрування (CTR, CBC) не повинно застосовуватися ізольовано. Необхідно використовувати **автентифіковане шифрування з прив'язаними даними (AEAD)**, зокрема **AES-GCM** або **ChaCha20-Poly1305**.

## 3. СТРАТЕГІЯ СИМЕТРИЧНОГО ЗАХИСТУ В ПРОЄКТІ LIKEDBYGENRE (ПУНКТИ 7–9)

### 3.1. Ідентифікація чутливих даних проєкту
У застосунку `LikedByGenre (SSS)` визначено такі категорії даних, що потребують симетричного криптографічного захисту:
1. **Персональні сесійні токени Spotify Web API:**
   - `access_token` — надає повноваження на читання приватної бібліотеки та створення плейлистів;
   - `refresh_token` — довготривалий токен, компрометація якого дозволяє безстроково керувати Spotify-акаунтом.
2. **Конфігураційні секрети платформи:**
   - `Spotify:ClientSecret` — приватний ключ застосунку;
   - Сесійні ключі підпису Cookie `LikedByGenre.Auth`.

### 3.2. Вибір криптографічного примітиву та режиму
Обрано міжнародний стандарт **AES-256-GCM (Galois/Counter Mode, AEAD)**:
- **Алгоритм:** Advanced Encryption Standard з довжиною ключа **256 бітів** (забезпечує стійкість проти квантових атак алгоритму Гровера на рівні 128 біт безпеки).
- **Режим GCM:** Поєднує лічильниковий режим CTR для шифрування з множенням у полі Галуа $GF(2^{128})$ для генерації автентифікаційної мітки GMAC.
- **Nonce (Вектор одноразового використання):** Розмір **96 бітів (12 байтів)**. Для кожної операції шифрування формується свіжий псевдовипадковий Nonce за допомогою криптографічно стійкого генератора `RandomNumberGenerator.Fill()`.
- **Authentication Tag:** Розмір **128 бітів (16 байтів)**. Гарантує виявлення будь-якої спроби модифікації або пошкодження шифротексту.

### 3.3. Формат криптографічного пакета
Результат шифрування серіалізується в єдиний контейнер:
```
+---------------------+---------------------+------------------------------+
|   Nonce (12 байт)   |    Tag (16 байт)    |     Ciphertext (N байт)      |
+---------------------+---------------------+------------------------------+
```
Фінальний масив байтів кодується у формат **Base64**, придатний для збереження в базі даних SQL Server, конфігураційних сховищах або захищених сесіях.

### 3.4. Керування ключами та порядок ротації
- **Зберігання ключів:** Ключ симетричного шифрування винесено за межі коду та Git-репозиторію. У середовищі розробки використовується `.NET User Secrets` (`Security:EncryptionKey`), у Production — захищені змінні оточення ОС або Azure Key Vault.
- **Детермінована генерація для резервного відновлення:** За відсутності налаштованого ключа використовується derivation на базі SHA-256 від системного секрету `ClientSecret`.
- **Ротація ключів:** Планова ротація здійснюється кожні 90 днів. Застосунок підтримує схему версіонування ключів для безшовного перешифрування наявних сесій.

### 4.2. Реалізація автентифікованого шифрування AES-256-GCM
Створено службу [`AesGcmEncryptionService.cs`](file:///C:/Users/Asus/Desktop/БПЗ/src/LikedByGenre/Services/AesGcmEncryptionService.cs):

```csharp
using System.Security.Cryptography;
using System.Text;
using Microsoft.Extensions.Configuration;

namespace LikedByGenre.Services;

public class AesGcmEncryptionService : ISymmetricEncryptionService
{
    private const int NonceSizeBytes = 12; // 96 біт Nonce
    private const int TagSizeBytes = 16;   // 128 біт Auth Tag
    private readonly byte[] _key;

    public AesGcmEncryptionService(IConfiguration configuration)
    {
        var configuredKey = configuration["Security:EncryptionKey"];
        if (!string.IsNullOrWhiteSpace(configuredKey) && configuredKey.Length == 64)
        {
            _key = Convert.FromHexString(configuredKey);
        }
        else
        {
            var secretSeed = configuration["Spotify:ClientSecret"] 
                ?? "LikedByGenre_Master_Encryption_Seed_2026_Key!";
            _key = SHA256.HashData(Encoding.UTF8.GetBytes(secretSeed));
        }
    }

    public AesGcmEncryptionService(byte[] key)
    {
        if (key == null || key.Length != 32)
            throw new ArgumentException("Ключ повинен бути 256-бітним (32 байти).");
        _key = (byte[])key.Clone();
    }

    public string Encrypt(string plainText)
    {
        if (plainText is null) throw new ArgumentNullException(nameof(plainText));

        byte[] plainBytes = Encoding.UTF8.GetBytes(plainText);
        byte[] nonce = new byte[NonceSizeBytes];
        RandomNumberGenerator.Fill(nonce); // Свіжий Nonce для кожної операції

        byte[] cipherBytes = new byte[plainBytes.Length];
        byte[] tag = new byte[TagSizeBytes];

        using (var aesGcm = new AesGcm(_key, TagSizeBytes))
        {
            aesGcm.Encrypt(nonce, plainBytes, cipherBytes, tag);
        }

        // Формування контейнера: [Nonce (12B)] + [Tag (16B)] + [Ciphertext (NB)]
        byte[] package = new byte[NonceSizeBytes + TagSizeBytes + cipherBytes.Length];
        Buffer.BlockCopy(nonce, 0, package, 0, NonceSizeBytes);
        Buffer.BlockCopy(tag, 0, package, NonceSizeBytes, TagSizeBytes);
        Buffer.BlockCopy(cipherBytes, 0, package, NonceSizeBytes + TagSizeBytes, cipherBytes.Length);

        return Convert.ToBase64String(package);
    }

    public string Decrypt(string cipherPackageBase64)
    {
        if (string.IsNullOrWhiteSpace(cipherPackageBase64))
            throw new ArgumentException("Шифротекст не може бути порожнім.");

        byte[] package = Convert.FromBase64String(cipherPackageBase64);
        if (package.Length < NonceSizeBytes + TagSizeBytes)
            throw new CryptographicException("Неприпустимий розмір пакета.");

        byte[] nonce = new byte[NonceSizeBytes];
        byte[] tag = new byte[TagSizeBytes];
        int cipherLen = package.Length - NonceSizeBytes - TagSizeBytes;
        byte[] cipherBytes = new byte[cipherLen];

        Buffer.BlockCopy(package, 0, nonce, 0, NonceSizeBytes);
        Buffer.BlockCopy(package, NonceSizeBytes, tag, 0, TagSizeBytes);
        Buffer.BlockCopy(package, NonceSizeBytes + TagSizeBytes, cipherBytes, 0, cipherLen);

        byte[] plainBytes = new byte[cipherLen];

        using (var aesGcm = new AesGcm(_key, TagSizeBytes))
        {
            // Decrypt автоматично перевіряє мітку tag.
            // При будь-якій модифікації шифротексту викидається CryptographicException.
            aesGcm.Decrypt(nonce, cipherBytes, tag, plainBytes);
        }

        return Encoding.UTF8.GetString(plainBytes);
    }

    public bool TryDecrypt(string cipherPackageBase64, out string? plainText)
    {
        try
        {
            plainText = Decrypt(cipherPackageBase64);
            return true;
        }
        catch (Exception)
        {
            plainText = null;
            return false;
        }
    }
}
```

## 7. ВИСНОВКИ
1. У процесі виконання лабораторної роботи №6 практично досліджено особливості блокових та потокових методів симетричного шифрування, їхні режими роботи (ECB, CBC, CTR, GCM) та вимоги до криптографічної стійкості.
2. Проведено практичну атаку відомого відкритого тексту (Known-Plaintext Attack) на режим **AES-CTR** за умов повторного використання початкового вектора ($IV$). 3. Обґрунтовано необхідність використання автентифікованого шифрування (AEAD) для захисту сесійних токенів Spotify Web API та конфігураційних параметрів веб-застосунку **LikedByGenre**.
