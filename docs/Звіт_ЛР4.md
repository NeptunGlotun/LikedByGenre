### 2.2. Попарна перевірка хешів та рядків (Пункт 8)

| Вхідний рядок \ Перевірений Хеш | Хеш №1 (із рядка 72 б) | Хеш №2 (із рядка 73 б) | Хеш №3 (із рядка 82 б) | Хеш №4 (із рядка 71 б) |
|---|:---:|:---:|:---:|:---:|
| **Рядок №1 (72 байти)** | **MATCH (True)** | **MATCH (True)** | **MATCH (True)** | FAIL (False) |
| **Рядок №2 (73 байти)** | **MATCH (True)** | **MATCH (True)** | **MATCH (True)** | FAIL (False) |
| **Рядок №3 (82 байти)** | **MATCH (True)** | **MATCH (True)** | **MATCH (True)** | FAIL (False) |
| **Рядок №4 (71 байт)** | FAIL (False) | FAIL (False) | FAIL (False) | **MATCH (True)** |

#### Висновки щодо обмеження BCrypt (72 байти):
1. **Причина явища:** Алгоритм BCrypt побудований на основі шифру Blowfish. Внутрішня таблиця ключів Blowfish (`P-array`) розширюється за допомогою 18 32-бітних слів, що обмежує максимальну довжину оброблюваного ключа **рівно 72 байтами** ($18 \times 4 = 72$). Будь-які байти після 72-го ігноруються алгоритмом і відкидаються.
2. **Аналіз результатів:**
   - Рядки №1 (72 б), №2 (73 б) та №3 (82 б) мають **ідентичні перші 72 байти**. Додані символи (`1` або `X9kLm2P7qR`) знаходяться за межею 72 байтів. Через це функція перевірки `BCrypt.Verify()` повертає `True` для будь-якої комбінації цих трьох рядків та їхніх хешів!
   - Рядок №4 має довжину 71 байт (символ на 72-й позиції відсутній). Тому він відрізняється від Рядків №1–3 на рівні перших 72 байт і успішно валідується **виключно** проти Хешу №4.
3. **Практична рекомендація для безпеки:** Якщо в системі використовуються паролі, довші за 72 байти, їх необхідно попередньо хешувати швидкою функцією (наприклад, SHA-256 або SHA-512) перед передачею в BCrypt, або застосовувати сучасніші алгоритми без такого обмеження (зокрема, **Argon2id**).

### 2.3. Дослідження стійкості до перебору: SHA-256 проти BCrypt (Пункти 9–13)

- **Контрольний рядок (п. 9):** `pass: Рябчук`
- **Хеш №5 (SHA-256, п. 11):**  
  `7b00d81ec4b0b6cb44dbc42befaaa1f3dc6ecd3ab8d8394188512768de8e17ea`
- **Хеш №6 (BCrypt, workFactor = 12, п. 12):**  
  `$2a$12$zE941rJfSBGX4hg7sFFiSOwKE8Xn1c/Vi625H4cIyAi7Mghpk0kL6`

#### Результати роботи скрипта атаки перебором (словник з 20 слів, правильний пароль на 20-й позиції):

| Параметр порівняння | SHA-256 (Хеш №5) | BCrypt workFactor=12 (Хеш №6) |
|---|---|---|
| **Кількість перевірених кандидатів** | 20 | 20 |
| **Результат атаки** | Знайдено: `pass: Рябчук` | Знайдено: `pass: Рябчук` |
| **Загальний час перебору** | **0.2753 мс** (0.000275 с) | **8078.82 мс** (8.0788 с) |
| **Середній час на 1 пароль** | **~0.0137 мс** | **~403.94 мс** |
| **Співвідношення швидкості** | Базова швидкість | **BCrypt у 29 346 разів повільніший!** |

#### Висновки щодо стійкості:
1. **SHA-256:** Є криптографічною хеш-функцією загального призначення, розрахованою на максимальну продуктивність обчислення даних. Через надзвичайно високу швидкість зловмисник на стандартному споживчому обладнанні з GPU здатен перевіряти десятки мільярдів хешів на секунду, що робить SHA-256 **небезпечним і непридатним** для зберігання паролів користувачів.
2. **BCrypt (cost = 12):** Є спеціалізованою функцією формування ключа (KDF), яка навмисно вимагає значних обчислювальних ресурсів ($2^{12} = 4096$ ітерацій розширення ключа). Перевірка одного пароля займає ~400 мс (непомітно для людини під час входу, але перебір навіть невеликого словника на 1 млн паролів займе понад **4.6 діб** на один потік). Крім того, наявність вбудованої випадкової солі захищає від використання Rainbow Tables.

## 3. РЕАЛІЗАЦІЯ В ПРОЄКТІ LIKEDBYGENRE (ПУНКТИ 15–19)

### 3.1. Архітектура автентифікації та авторизації

У веб-застосунку реалізовано **гібридну дворівневу систему**:

1. **Локальна автентифікація (фактор знання):**
   - Користувачі реєструються через логін (`Username`) та пароль (`Password`).
   - Паролі перевіряються на мінімальну довжину (8 символів).
   - Зберігання пароля здійснюється виключно у вигляді хешу **BCrypt із сіллю** (`workFactor = 12`) у таблиці `Users` локальної бази даних SQL Server.
   - Механізм перевірки входу захищений від розкриття наявності облікового запису (повертається узагальнене повідомлення: *"Неправильний логін або пароль"*).
2. **Федеративна автентифікація (фактор володіння акаунтом):**
   - Інтеграція зі Spotify Accounts Service за протоколом **OAuth 2.0 з PKCE** (`options.UsePkce = true`).
3. **Керування сесією та авторизація:**
   - Після успішної перевірки автентифікаційних даних користувачу випускається захищена сесійна Cookie `LikedByGenre.Auth` (`HttpOnly`, `SameSite=Lax`, `SecurePolicy=SameAsRequest`, термін дії 8 годин, ковзне оновлення).
   - Захист сторінок медіатеки, списків жанрів та створення плейлистів забезпечується атрибутом `[Authorize]`.

### 3.2. Ключові фрагменти коду реалізації

#### 2. Реєстрація користувача та хешування BCrypt (`AccountController.cs`):
```csharp
[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> Register(string username, string password, string confirmPassword)
{
    if (string.IsNullOrWhiteSpace(username) || string.IsNullOrWhiteSpace(password))
    {
        TempData["Error"] = "Всі поля обов'язкові для заповнення.";
        return View();
    }

    if (password.Length < 8)
    {
        TempData["Error"] = "Пароль повинен містити щонайменше 8 символів.";
        return View();
    }

    if (password != confirmPassword)
    {
        TempData["Error"] = "Паролі не збігаються.";
        return View();
    }

    var normalizedUsername = username.Trim();
    var exists = await _db.Users.AnyAsync(u => u.Username == normalizedUsername);
    if (exists)
    {
        TempData["Error"] = "Користувач із таким іменем уже існує.";
        return View();
    }

    // Безпечне хешування пароля за допомогою BCrypt із сіллю та workFactor 12
    var passwordHash = BCrypt.Net.BCrypt.HashPassword(password, workFactor: 12);

    var newUser = new User
    {
        Username = normalizedUsername,
        PasswordHash = passwordHash,
        CreatedAt = DateTime.UtcNow
    };

    _db.Users.Add(newUser);
    await _db.SaveChangesAsync();

    TempData["Success"] = "Обліковий запис успішно створено. Увійдіть за допомогою своїх облікових даних.";
    return RedirectToAction(nameof(Login));
}
```

#### 3. Перевірка пароля та захист від витоку інформації (`AccountController.cs`):
```csharp
[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> Login(string username, string password)
{
    if (string.IsNullOrWhiteSpace(username) || string.IsNullOrWhiteSpace(password))
    {
        TempData["Error"] = "Вкажіть логін та пароль.";
        return View();
    }

    var user = await _db.Users.FirstOrDefaultAsync(u => u.Username == username.Trim());
    
    // Захист від user enumeration: узагальнене повідомлення та безпечна перевірка BCrypt.Verify
    if (user == null || !BCrypt.Net.BCrypt.Verify(password, user.PasswordHash))
    {
        TempData["Error"] = "Неправильний логін або пароль.";
        return View();
    }

    var claims = new List<Claim>
    {
        new(ClaimTypes.NameIdentifier, user.SpotifyId ?? user.Username),
        new(ClaimTypes.Name, user.Username)
    };

    var identity = new ClaimsIdentity(claims, CookieAuthenticationDefaults.AuthenticationScheme);
    var principal = new ClaimsPrincipal(identity);

    await HttpContext.SignInAsync(
        CookieAuthenticationDefaults.AuthenticationScheme,
        principal,
        new AuthenticationProperties
        {
            IsPersistent = true,
            ExpiresUtc = DateTimeOffset.UtcNow.AddHours(8)
        });

    return RedirectToAction("Index", "Library");
}
```

Під час виконання лабораторної роботи №4:
1. Було досліджено внутрішні особливості алгоритму **BCrypt**, експериментально підтверджено наявність 72-байтового ліміту довжини вхідного рядка (через архітектуру ключового розкладу Blowfish) та продемонстровано колізію валідації паролів, що відрізняються лише за межами 72 байтів.

3. У вихідному коді проєкту `LikedByGenre` реалізовано повноцінну локальну підсистему автентифікації на базі `BCrypt.Net-Next`, створено таблицю `Users` у Microsoft SQL Server, налаштовано безпечне керування сесіями (Cookie Authentication), авторизаційний контроль доступу (`[Authorize]`) та захист від атак CSRF (`[ValidateAntiForgeryToken]`), повністю зберігши працездатність Spotify API та сортування пісень.
